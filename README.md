# ReadBibleTrack

A shared Bible reading tracker for couples, families and small circles of friends.
One Expo codebase serving iOS, Android and the web.

The point of the app is not the reader — it is the circle. If a feature works
just as well alone, it is not a priority.

## Running it

```sh
npm install
npm start          # then press i, a, or w
npm run web        # web only
npm test           # unit tests, no test framework needed
npm run typecheck
npm run ingest     # rebuild the bundled scripture database
```

`npm start` prints a QR code. Scan it with Expo Go to run on a real phone —
that works today without Xcode. iOS *simulator* builds need the full Xcode
install, not just the Command Line Tools.

## Layout

```
src/
  app/          Expo Router routes — these become both screens and web URLs
  bible/        canon, verse ids, range algebra, references, versification
  scripture/    opening a bundled translation and reading verses out of it
  progress/     what has been read, as ranges over verse ids
  components/   themed primitives
  constants/    design tokens (theme.ts)
  hooks/
scripts/        ingestion — run by hand, never bundled
assets/bibles/  one read-only SQLite file per translation
types/          ambient declarations
```

## Verse ids

Every verse in the canon is one sortable integer:

```
book * 1_000_000  +  chapter * 1_000  +  verse

Genesis 1:1      ->  1_001_001
John 3:16        -> 43_003_016
Revelation 22:21 -> 66_022_021
```

Reading progress is stored as `[start, end]` ranges over these ids, never as a
list of verses and never as a mutable percentage. Two things follow:

- **Progress is translation-independent.** Reading Genesis in Malayalam writes
  exactly the same rows as reading it in English, so a family reading in
  different languages still shares one progress bar.
- **Group progress is one SQL aggregate**, not a row per verse per person.

Because no chapter has more than 176 verses (Psalm 119), `999` is a safe open
upper bound for a chapter. That is why `chapterSpan` and `bookSpan` work without
any versification data at all.

Counting *actual* verses does need that data, and it lives in
`src/bible/versification.ts`, over a table generated by the ingestion script.
Everything there is built on one idea: every verse has an **ordinal**, its index
from Genesis 1:1, so counting a range is subtraction no matter what it spans.
`countVerses([canonSpan()])` returns 31,103 even though `canonSpan` was built
with no idea how long any chapter is.

`src/bible/verse-id.ts` is the load-bearing file. The book numbering in
`canon.ts` is baked into every id ever stored, so it must never be renumbered.

## Scripture text

Text is **bundled in the app** as a read-only SQLite file per translation, not
served from our backend. It works offline, costs nothing per read, and keeps
the database free of scripture entirely.

Only translations that are public domain or CC BY-SA get bundled. Every shipped
translation must be listed in `LICENSES.md` with its source URL, licence and
download date — `npm run ingest` regenerates that file from the metadata inside
each database, so it cannot drift. Copyrighted versions (NIV, ESV) can only come
from an API under licence and cannot be bundled offline.

`npm run ingest` downloads USFM, parses it, checks it against `canon.ts` and
writes `assets/bibles/<id>.db`: one row per verse keyed by verse id, the
paragraph style so poetry reads as poetry, and the headings that stand before a
verse rather than inside it — including all twenty-two acrostic titles in
Psalm 119.

### What the database keeps, and what it does not

Ingestion is lossy on purpose: the database is a projection of the USFM, and
anything not captured is only recoverable by ingesting again from source. That
makes this list a decision rather than an accident.

| Kept | |
|---|---|
| Verse text, keyed by verse id | the reader |
| Paragraph style (`p`, `q1`, `q2`) | prose reads as prose, poetry as poetry |
| Headings before a verse | psalm superscriptions, Psalm 119's acrostics |
| Words of Jesus (`\wj`) | 2,290 spans — red-letter reading |
| Footnotes (`\f`) | 1,228 notes — translator's reasoning |

| Dropped | Why |
|---|---|
| Cross references (`\x`) | 340 — a navigation feature with no UI yet |
| Strong's numbers (`\w`) | 683,868 tags, ~3.3 MB — would near enough double a bundled translation for a word-study feature this app does not need |

Red-letter spans are stored as character offsets into the verse text, not as
markup, so the reader slices the string and never parses anything at runtime.
The offsets are computed while the cleaned text is assembled — `\wj` wraps text
that still contains `\w` tags, so they cannot be measured against the raw
source.

### Translations are separate, and selectable

Each translation is its own database in `assets/bibles/`. They are never merged,
and switching between them opens a different file:

| | Verses | Notes | Red letter |
|---|---|---|---|
| **WEB** World English Bible | 31,103 | 1,228 | yes |
| **BSB** Berean Standard Bible | 31,086 | 4,808 | no |
| **KJV** King James Version | 31,102 | 6,959 | yes |

`src/bible/translations.ts` is the registry the app picks from, generated from
the databases themselves so it cannot drift from what is shipped. The asset map
that hands each file to Metro is separate (`src/scripture/assets.ts`) only
because `require()` needs literal paths, which a test running under plain `node`
could not resolve.

Which translation someone reads is **a display preference and nothing more**.
Progress is stored as verse ids, so a circle reading three different
translations still shares one progress bar, and switching never touches a stored
range. That is the whole reason for the verse-id design.

Only public domain and CC BY-SA texts can be bundled. The ESV and NIV cannot:
their licences forbid redistribution, and the ESV API caps caching at 500 verses
against a canon of 31,105 — see `LICENSES.md` for what is shipped.

### Keeping a device up to date

`expo-sqlite` copies a bundled asset into local storage on first launch and
reuses that copy forever. A translation corrected by a later ingest would never
reach anyone who already had it, so the registry carries a short content hash of
each file and the app forces a fresh extract when it differs from the copy it
last wrote. Re-ingesting is enough; nothing else has to be bumped by hand.

### Reading it at runtime

`expo-sqlite` opens the bundled file, copying it into local storage on first
launch and reading from there afterwards:

```tsx
<SQLiteProvider databaseName="web.db" assetSource={{ assetId: require('@/assets/bibles/web.db') }}>
```

The web build is the awkward one. It runs SQLite as WebAssembly and keeps the
database in OPFS, which needs `SharedArrayBuffer`, which browsers only hand to
cross-origin-isolated pages. Both halves are already configured:

- `metro.config.js` adds `wasm` to `assetExts` — Metro does not treat it as an
  asset by default — and sets the isolation headers on the dev server.
- The `expo-router` plugin in `app.json` sets the same headers on a deployed
  build. **Any host serving the web build has to send them**, or SQLite will not
  start there. That rules out some static hosts.

Web pays 4.4 MB for the database and 607 KB for the WASM on first load, cached
after. Native pays only the 4.4 MB, inside the app download.

### Versification is not universal

Verse numbering differs between translations, so the generated table is written
once and afterwards only *compared*. Ingesting a second translation prints where
it disagrees and changes nothing, because every stored range is measured against
those counts. Overwriting takes `--versification`, deliberately.

The table is the **union of every bundled translation**, and it only ever grows.
That matters: the WEB places the Romans doxology at the end of chapter 14, while
the KJV and BSB place it at the end of chapter 16. If the table followed only
one of them, the others would carry verses that no range could measure, because
an ordinal stops at the last verse the table knows about. Reserving the highest
number any of them uses fixes that, and is safe in a way that picking one is
not — growing reserves more ids, it never moves a range that is already stored.

So the canon totals 31,105 here: three more than the KJV's familiar 31,102,
because both numbering traditions for Romans are reserved. Everywhere outside
Romans 14 and 16 the three agree exactly. Where a translation numbers a verse it does not carry —
Acts 8:37, Romans 16:25 — the row is kept with empty text, so the id stays
reserved and a range means the same thing in every translation. The footnote
saying *why* it is empty is stored against it, so the reader can explain the gap
rather than showing a blank line.

## Getting around

One navigation component with one breakpoint: a bar along the bottom on a
phone, a rail down the side past 900px. Bottom tabs on a 1440px display are a
phone app in a costume.

The reader is deliberately excluded from both. Reading is the one thing here
that deserves the whole screen, so a chapter is left with "‹ Today" rather than
a bar competing with the text.

### The app must open without a network

`supabase.auth.getSession()` does not merely fail when the server is
unreachable — it *hangs*, because supabase-js retries an expiring token with
backoff and the promise never settles. A plain `catch` never runs. Without a
deadline the gate renders nothing for ever: a blank screen, no message, no way
out.

So the session lookup races a five second timer. Reading needs no network at
all — bundled scripture, local progress — and waiting on one is the wrong
default.

## Status

Phase 2. The loop closes: open today's reading, read it in whichever of three
translations you like, mark it read, and watch the count move. Progress is
stored locally as ranges over verse ids, in its own database that survives a
translation being re-ingested.

The reader renders what the ingestion bothered to keep — poetry as poetry,
psalm superscriptions and Psalm 119's acrostic letters as headings, section
titles where a translation has them, footnote markers where they hang, and the
words of Jesus in red where a translation marks them.

Next: circles. Everything so far works alone, which by this project's own
measure means none of it is the point yet.
